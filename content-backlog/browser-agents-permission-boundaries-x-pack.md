## Standalone X options

### Option 1 — authority

A logged-in browser session is not just context.

It is authority.

That changes the product question from “can the agent click?” to “which clicks should be impossible without approval?”

### Option 2 — four boundaries

Browser agents need more than read/write permissions.

A useful default is:

read silently,
draft freely,
ask before submit,
leave a receipt after state change.

### Option 3 — traceability

Fast browser control is impressive.

Traceable browser control is deployable.

If an agent can use a logged-in session, the boring parts matter: what was in scope, what was approved, what changed, and how access gets revoked.

### Option 4 — category line

The click loop is getting commoditized.

The permission boundary is the product.

### Option 5 — practical operator angle

A browser agent that can fill a form is useful.

A browser agent that knows when not to submit the form is much more useful.

### Option 6 — session scope

“Can use browser” is too broad once the browser is logged in.

The useful grant is narrower:
this session, this task, these sites, these actions, this approval path, until revoked.

### Option 7 — state change gate

For browser agents, I’d separate two jobs:

1. gather context and prepare the work;
2. change live state.

The first can be fast. The second usually needs a gate.

### Option 8 — audit angle

A browser-agent receipt should answer simple questions:

what did it see,
what did it change,
who approved it,
and how do we stop or undo the delegation?
